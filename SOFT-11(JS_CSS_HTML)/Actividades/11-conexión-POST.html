Conectar el frontend de SICEN con la API

Objetivo: Conectar el formulario de SICEN con el endpoint POST de la API en NestJS usando fetch, probarlo con datos válidos e inválidos y continuar el backend con nuevas consultas, una modificación y una segunda colección relacionada.

Contexto

En el ejercicio anterior, el equipo programó en NestJS la primera colección de SICEN y probó sus endpoints con pruebas.http. Antes, en el ejercicio de validación, programó el formulario con sus reglas en JavaScript. Ahora se unen las dos partes: el usuario registra los datos desde la pantalla y estos llegan a MongoDB Atlas a través de la API.

El recorrido completo de un registro es: formulario → validación en JS → fetch (POST) → DTO → servicio → MongoDB Atlas → respuesta → mensaje al usuario.

Nota: los ejemplos usan la entidad CentroEducativo. Use las entidades y los requerimientos de su propio modelo.

Conectar el formulario con el POST

Use el formulario de SICEN que ya validaron con JavaScript (ejercicio de validación) y conéctelo con el endpoint POST del ejercicio anterior. Esta es la estructura sugerida; complete las partes marcadas con …:

// Dirección del backend: defínala una sola vez y úsela en todas las peticiones
const API_URL = "http://localhost:3000";

// ---------- Elementos del HTML ----------
const formulario = document.getElementById("frmCentro");
const inputNombre = document.getElementById("txtNombre");
// … un elemento por cada campo del formulario

// ---------- 1. Validar (ya lo tienen del ejercicio de validación) ----------
function validar() {
    let hayError = false;
    // … reglas: obligatorios, expresiones regulares, rangos
    return !hayError;
}

// ---------- 2. Enviar al servidor ----------
async function registrarCentro() {
    // Los nombres deben ser IGUALES a los del DTO del backend
    const datos = {
        nombre: inputNombre.value.trim(),
        // … los demás campos; el subdocumento como objeto: direccion: { … }
    };

    try {
        const respuesta = await fetch(`${API_URL}/centros-educativos`, {
            method: "POST",
            headers: { "Content-Type": "application/json" },  // el body es JSON
            body: JSON.stringify(datos)                        // objeto → texto
        });
        const resultado = await respuesta.json();              // texto → objeto

        if (!respuesta.ok) {
            // 400 (datos inválidos), 409 (valor repetido)…
            // resultado.message puede ser un TEXTO o un ARREGLO de textos
            mostrarErrorServidor(resultado);
            return;
        }

        // 201: se registró. resultado es el documento creado
        Swal.fire({
            icon: "success",
            title: "Centro registrado",
            text: `${resultado.nombre} se registró correctamente.`
        });
        formulario.reset();
    } catch (error) {
        // El servidor está apagado o no responde
        // … mostrar un mensaje con Swal.fire
    }
}

// ---------- 3. Evento ----------
formulario.addEventListener("submit", (evento) => {
    evento.preventDefault();   // evita que la página se recargue
    if (validar()) {
        registrarCentro();
    }
});

Requisitos

  • Activar app.enableCors() en el main.ts del backend, para que la página (Live Server, puerto 5500) pueda consultar la API (puerto 3000).
  • Construir el objeto con los mismos nombres de propiedades que el DTO. El subdocumento se envía como un objeto dentro del objeto.
  • No enviar los campos opcionales vacíos: agregarlos al objeto solo si el usuario los escribió.
  • Enviar con fetch, method: "POST", el encabezado Content-Type y JSON.stringify.
  • Revisar respuesta.ok: mostrar un mensaje de éxito con un dato que devolvió el servidor (por ejemplo, el nombre) y limpiar el formulario.
  • Programar mostrarErrorServidor(datos): si datos.message es un arreglo, mostrar un mensaje por línea; si es un texto, mostrarlo tal cual.
  • Mostrar un mensaje claro en el catch cuando el servidor no responde (no solo console.log).
  • Usar SweetAlert2 para todos los mensajes. No se permite alert().

Importante: un error 400 o 409 no entra al catch, porque el servidor sí respondió. Esos casos se manejan con respuesta.ok. El catch solo atrapa los errores de conexión.

Probar con datos válidos e inválidos

La validación del frontend ayuda al usuario, pero cualquiera puede saltársela enviando la petición directamente con REST Client o Postman. La validación del backend (DTO y esquema) protege los datos. Por eso se prueba desde los dos lados.

Requisitos

  • 3 pruebas válidas desde el formulario. Comprobar en MongoDB Atlas que cada documento se guardó con la estructura del diagrama (incluido el subdocumento si aplica).
  • 3 pruebas inválidas desde el formulario: el JavaScript debe detenerlas sin enviar la petición.
  • 1 prueba de valor repetido (409) y 1 con el servidor apagado, ambas desde el formulario, verificando el mensaje que ve el usuario.
  • Si una regla existe solo en el frontend o solo en el backend, agregarla al otro lado y anotar el cambio.
  • Completar la columna Resultado obtenido. Si no coincide con el esperado, corregir el código y repetir la prueba.
