Recomendaciones para validar formularios con JavaScript

¿Para qué validar? Validar en el navegador ayuda a que la persona corrija sus datos antes de enviarlos, con mensajes inmediatos y claros. Una buena validación no castiga al usuario: le explica qué está mal y cómo corregirlo.

Preparar el HTML antes de escribir JavaScript

  • Cada campo debe tener un id único: es la forma más sencilla de seleccionarlo con JS.
  • Cada campo debe tener su <label for="…"> asociado: los lectores de pantalla lo leen y, al hacer clic en la etiqueta, el campo recibe el foco.
  • Agregue debajo de cada campo un contenedor vacío para el mensaje de error, con un id fácil de deducir (por ejemplo, error-correo para el campo correo).
  • Enlace el campo con su mensaje usando aria-describedby: así el lector de pantalla también lee el error.
  • Use novalidate en el <form> para controlar los mensajes con JS, pero mantenga required en los campos obligatorios: sigue informando a las tecnologías de asistencia.
  • Indique visualmente los campos obligatorios (por ejemplo, con *) y explique al inicio qué significa.
  • Use el type correcto (email, tel, number, date): en el celular muestra el teclado adecuado.

Ejemplo de un campo bien preparado 

<label for="correo" class="form-label">Correo electrónico *</label>
<input type="email" id="correo" class="form-control"
       required aria-describedby="error-correo">
<div class="invalid-feedback" id="error-correo"></div>

Capturar los datos correctamente

  • Seleccione los elementos una sola vez, al inicio del archivo, y guárdelos en constantes con nombres claros (inputCorreo, selectProvincia).
  • Use getElementById para un elemento con id, querySelector para el primero que cumpla un selector de CSS y querySelectorAll para varios.
  • Lea el valor cuando se valida, no al cargar la página: al inicio el campo está vacío.
  • Use .trim() para quitar espacios de los extremos: un texto con solo espacios no es un dato válido.
  • Recuerde que .value siempre es texto: convierta con Number() antes de comparar cantidades.
  • En checkbox y switch se revisa .checked (true o false), no .value.
  • Para grupos de checkbox o un select múltiple, cuente los marcados con querySelectorAll(":checked").
  • En un select, la primera opción ("Seleccione…") debe tener value="" para poder detectar que no se eligió nada.

Ejemplo 

// Se seleccionan una sola vez, al inicio
const inputCorreo = document.getElementById("correo");
const inputCantidad = document.querySelector("#cantidadEstudiantes");
const checkTerminos = document.getElementById("terminos");

// Se leen al validar
const correo = inputCorreo.value.trim();          // texto sin espacios extra
const cantidad = Number(inputCantidad.value);     // texto → número
const acepto = checkTerminos.checked;             // true o false
const niveles = document.querySelectorAll('input[name="niveles"]:checked').length;

Definir reglas claras y en orden

Revise cada campo en este orden y muestre solo el primer problema que encuentre:

  1. ¿Está vacío? → "Escriba su correo electrónico."
  2. ¿Tiene el formato correcto? (expresión regular) → "Revise el correo: debe tener el formato nombre@dominio.com."
  3. ¿Cumple las reglas del negocio? (rangos, fechas, relación entre campos) → "La fecha de cierre debe ser posterior a la de apertura."
  • Al validar un dato completo, la expresión regular debe tener ^ al inicio y $ al final; si no, basta con que una parte cumpla.
  • Guarde las expresiones regulares en constantes con nombre y un comentario de qué aceptan.
  • Sea flexible con el formato y estricto con el contenido: acepte "8888-1234" y "88881234"; acepte mayúsculas y minúsculas en un correo.
  • Pruebe cada regla con datos válidos, inválidos y límite (el mínimo, el máximo, 0, un texto vacío).

Escribir mensajes de error útiles

  • Diga qué está mal y cómo corregirlo, idealmente con un ejemplo.
  • Use un lenguaje amable y sin culpas: "Escriba su teléfono" en lugar de "Error: dato inválido".
  • Muestre el mensaje junto al campo y déjelo visible hasta que se corrija.
  • No dependa solo del color: agregue texto y un ícono (hay personas que no distinguen el rojo del verde).
  • Evite mensajes técnicos como "regex no coincide" o "NaN".

Mostrar los errores en pantalla

  • Cree dos funciones reutilizables: una que marque el error y otra que marque el campo correcto. Así no repite código en cada validación.
  • Use las clases de Bootstrap is-invalid e is-valid con classList.add() y classList.remove().
  • Escriba el mensaje con textContent, nunca con innerHTML, cuando incluya datos escritos por el usuario.
  • Si hay varios errores, muestre un resumen (modal de Bootstrap o SweetAlert2) con la lista de campos por corregir.
  • Después del resumen, lleve el foco al primer campo con error para que la persona empiece a corregir de inmediato.
  • Cuando todo esté correcto, confirme con un mensaje de éxito claro.

Ejemplo de funciones reutilizables 

function marcarError(input, mensaje) {
    input.classList.add("is-invalid");
    input.classList.remove("is-valid");
    const divError = document.getElementById("error-" + input.id);
    divError.textContent = mensaje;
}

function marcarCorrecto(input) {
    input.classList.remove("is-invalid");
    input.classList.add("is-valid");
    document.getElementById("error-" + input.id).textContent = "";
}

// Llevar el foco al primer campo con error
document.querySelector(".is-invalid").focus();

Validar en el momento adecuado

  • No muestre errores al cargar la página: la persona todavía no ha escrito nada.
  • Valide al presionar el botón de enviar o guardar (evento click o submit).
  • Después del primer intento, vuelva a validar mientras escribe (evento input) para que el error desaparezca en cuanto se corrige.
  • Si ayuda, dé formato automático (agregar el guion del teléfono, permitir solo números en un código), pero sin borrar lo que la persona escribió.
  • No deshabilite el botón de enviar sin explicar por qué: es mejor dejarlo activo y mostrar qué falta.

Evitar alert() para comunicar errores

  • Bloquea la página hasta que se cierra.
  • No se puede personalizar: sin colores, íconos, listas ni botones propios.
  • Muestra el dominio ("127.0.0.1 dice:"), lo que confunde o parece un engaño.
  • El usuario puede marcar "No permitir más diálogos" y dejar de ver los errores.
  • Algunos navegadores lo bloquean dentro de Moodle u otros iframes.
  • Al cerrarlo, el mensaje desaparece y la persona debe recordar qué decía.
Alternativas: mensajes junto a cada campo, un modal de Bootstrap o SweetAlert2.

Recordar los límites de validar en el navegador

  • La validación con JS mejora la experiencia, pero no protege los datos: cualquier persona puede desactivar JavaScript o modificarlo con F12.
  • Por eso, las mismas reglas deben repetirse en el servidor (en el curso: Express y los esquemas de Mongoose).
  • Nunca inserte con innerHTML un texto escrito por el usuario: use textContent para evitar que se ejecute código.
  • No guarde contraseñas ni datos personales en localStorage.

Importante: validar en el cliente es para el usuario; validar en el servidor es para el sistema. Se necesitan ambas.

Lista de verificación antes de entregar

  • Cada campo tiene id, label y un contenedor para su mensaje de error.
  • Los elementos se seleccionan una sola vez, al inicio del archivo JS.
  • Los textos se limpian con trim() y los números se convierten con Number().
  • Se valida: vacío → formato → reglas del negocio.
  • Los mensajes dicen qué está mal y cómo corregirlo.
  • El error se ve con texto, no solo con color.
  • El foco va al primer campo con error.
  • No se usa alert().
  • Se probó con datos válidos, inválidos y límite.
  • El código tiene comentarios que explican la lógica.
